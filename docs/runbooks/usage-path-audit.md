### 抓到的缺陷：`chunk_id` 不是 UUID（`829806e`）

**现象**：`POST /api/v1/knowledge/search` 返回的 `chunk_id` 是
`9eac9177523794ed`（16 位 hex，Chroma 内部 id），不是 SQLite `doc_chunk.id`。

**后果**：**引用无法回溯到原文** —— 用户看到一条检索结果，点不回具体段落。
而「每条证据可点回原文」正是本项目（证据约束 + 引用可追溯）的核心能力。

**根因**：端点调的是 `service.search()`（直接返回索引层结果，id 未映射），
正确入口是 `service.search_for_context()` —— 内部走 `_attach_storage_ids()`，
按 `VectorIndex.chroma_id` 把索引 id 换成 `DocChunk.id` / `KnowledgeDoc.id`。

**为什么单测没抓到**：既有测试断言了「有结果」「数量对」，但**没断言 id 的形态**。
16 位 hex 和 UUID 在「有没有结果」这个维度上完全一样。

### 巡检纠正的两个**我的错误假设**

**① 角色名不是 `editor`，是 `admin` / `member` / `viewer`**

我按「owner/editor/viewer」写脚本，邀请 `editor` 被 422 拒绝。
**这是脚本错了，不是代码错了** —— 实际角色体系更简洁。

**② 学生版席位上上限是 3，不是 5**

脚本请求 5 席 → 403 `PLAN_SEAT_LIMIT`。**门禁工作正常**，是脚本参数错了。

> 教训：巡检脚本里的期望值必须**从代码/契约里核实**，不能凭直觉写。
> 这两次「失败」如果不去看响应体，很容易误报成产品缺陷。

## 复跑方式

```bash
# 三条脚本在本地（需能访问 10.0.10.2:48080）
python audit_1_knowledge.py    # 会注册新账号（注意注册限流 5 次/小时）
python audit_2_template.py
python audit_3_workspace.py    # 用固定账号 auditws_*，需先开通 student 套餐
```

**注意**：`auth_register` 限流 5 次/小时、`auth_login` 限流 10 次/60 秒。
连跑多条脚本会触发限流 —— 需要 `redis-cli FLUSHDB` 或改用固定账号。
