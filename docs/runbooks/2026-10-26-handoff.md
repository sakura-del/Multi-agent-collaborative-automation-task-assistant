### 3.1 用量看板（已完成，`b5bf912`）

交接时排在风险第一位是对的，但**实际发现的问题比「版式不好」严重得多**：

- **后端从来没记过 token 用量**：`sum_actual_tokens` 读顶层字段，生产载荷是嵌套的
  → `task.used_tokens` 全库恒为 0 → 看板「累计 token」永远 0，
  **且配额结算每次都退满（用户白嫖算力）**；
- 状态分布漏 `waiting_approval` → 「总数 27 / 分布 26」，差值不可见；
- 成功率没有分母；最近任务只有 8 位 UUID；
- 回填脚本把 28 个任务的 `updated_at` 刷掉（耗时显示 9708 分）——**已恢复**；
- 任务行 `<li @click>` 键盘不可达——已改 `<button>`。

已回填历史用量 169372 token 并独立 SQL 核对一致。设计记录见
`docs/superpowers/specs/2026-10-23-frontend-redesign-design.md` §4.14。

### 3.2 下一个页面（套餐页）的开局提醒

**先查「显示的数字有没有出处」**，别先改版式。用量看板这一页就是靠这条找到真缺陷的。
具体建议：

1. 打真实接口 `GET /billing/usage` 与 `GET /billing/plans`，把返回值和页面上的数字**逐个对**；
2. 注意 `reviews_remaining: null`（机构版不限）在页面上是怎么显示的——
   `null` 被当成 0 显示就会变成「额度已用完」；
3. `usedPercent` 的分母是 `monthly_reviews`，机构版是 `-1`（哨兵值），
   如果 `isUnlimited` 判断漏了某个分支，进度条会算出负数或 NaN。

**每个页面的工作方式**（照第六阶段的做法）：

1. **先量真实数据** → 从接口与页面的差异里找**真实缺陷**（不是版式偏好）
2. 写**失败测试**复现（断言要覆盖「这个值能不能用」，不只「格式合不合法」）
3. 实现 → 绿
4. **再量数值 + 结构化取证**验证
5. 诚实性验证：回退修复 → 必须变红
6. 全套门禁（**前端必须跑 `vue-tsc -b`**，见 AGENTS §5 #18）→ 提交 → 部署 →
   真实浏览器验证 → 文档 → 推送
7. 数据修复脚本必须**回查**，并确认「只改了想改的那一列」（AGENTS §5 #17）
