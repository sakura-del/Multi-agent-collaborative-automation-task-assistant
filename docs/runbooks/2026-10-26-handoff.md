但 `evidence_pool` 是空的。根因是**两条线互不相干**：

```

extract/write → LiteratureContextBuilder.build()   → evidence

        knowledge.search_for_context(user_id, query)   ← 只查知识库向量索引
```

写作 Agent 在没有任何证据的情况下生成内容。

`prepare_node` 合并两类证据 + `normalize_doi()` 去重合并 +

**元数据证据不含编造摘要** —— CSL 条目没有摘要字段，`abstract=""` 是故意的。
元数据证据只能支撑「存在这样一篇文献」，不能支撑「作者指出……」。

## 3.10 校验结论落库（`90dfd6a`，已完成）

计划：[2026-10-27-01-validation-persistence-plan.md](../superpowers/plans/2026-10-27-01-validation-persistence-plan.md)

### 缺陷

`validation_result` 表有 `passed` / `score` / `rule_results` / `llm_report` /
`report` / `validated_at` 六列，但**一条记录都没有**：

```bash
grep -r "ValidationResult(" backend/app   # 无结果
```

全 `app/` 里**没有任何代码实例化它**。校验结论只被塞进
`subtask.output_data` 的 JSON —— 不可查询、不可聚合、不可统计。

### 后果

| 场景 | 影响 |
| --- | --- |
| 排查「为什么转人工」 | 只能逐个任务拉 API 快照 |
| 统计校验通过率 | 做不到（`passed` 列形同虚设） |
| **量化 review 长度上限的影响面** | **做不到**（§3.9 就是因此无法量化） |

### 修法

新增 `ValidationRepository`（与 `EventRepository` 同构：只 flush 不 commit），
在 `persistence.py::on_result` 里接入。

**三个关键决定**：

1. **`score` 必须除以 100**：契约 `ValidationReport.score` 是 **0–100**，
   而列注释是 **0–1**。直接存 85.5 会让下游算出「8550% 通过率」。
   这种单位不一致**不报错、只静默算错**，所以有专门的 `normalize_score()` + 夹紧 + 测试；
2. **`output_data` 里的校验保持不动** —— 落库是新增，不删旧路径（快照/复盘还在读它）；
3. **无校验的节点不建行** —— 否则「校验通过率」的分母里混进没校验的节点。

### 真实任务验证

任务 `a849241a` → `completed`，5 个节点带校验结果：

| 查证项 | 结果 |
| --- | --- |
| 修复前表行数 | **0** |
| 修复后本任务行数 | **5**（与节点数一致） |
| `score` 在 0–1 | **5/5**（`min=1, max=1`） |
| `rule_results` 是 checks 明细 | ✅ 9 条 |
| `llm_report` 非空 | 5/5 |
| `passed` 可聚合 | ✅ `GROUP BY passed` → `t: 5` |

### 历史缺口的量化（本轮真正的价值）

```sql
SELECT
  (SELECT count(*) FROM subtask WHERE output_data::jsonb->'validation' <> 'null'::jsonb)
    AS subtasks_with_validation,
  (SELECT count(*) FROM validation_result) AS table_rows;
```

```

--------------------------+------------

```

**193 个节点有过校验结论，表里只有 5 行（都是本轮刚写的）。**
上一轮无法回答「review 长度上限影响过多少任务」，根因就是这个。

### 诚实性验证

回退 `on_result` 的落库调用 → **1 条变红**。

> 注意：**Repository 的 11 条单测仍然全绿**，只有接线测试变红。
> 没有接线测试就会出现「单测全过、表照样是空的」—— 正是本缺陷的原样重演。

  但**没有单独跑真实任务**；

### 一条 test，五个场景

| ⑤ | 移动端 390px | 编辑表单无横向溢出（`scrollWidth - clientWidth <= 1`） |

### 写这条 E2E 踩的三个坑

### 3.14.2 关键发现：**失败全部集中在最强画像**

```
single_agent_no_rag        15/15 completed
multi_agent_no_rag         15/15 completed
multi_agent_vector_rag     15/15 completed
multi_agent_hybrid_rerank  11/15 completed  ← 4 个 waiting_human
```

同一个课题在其他三个画像下全部 completed → 不是课题难，是画像特有。

**根因**（从 `validation_result` 表查证）：该画像证据最多（16~18 条），
模型引用时**编号捆绑混乱**（`E4的框架[E1][E2][E4][E5]`）、
**残留未替换占位符**（`'– 仅支持数据集用途'`）、**参考文献重复**（Ragas 出现两次）。

### 3.14.3 真实成功率（**不能只看 aggregate.csv 的 success**）

| 画像 | completed/总数 | 真实成功率 | `aggregate.csv` 的 success |
| --- | --- | --- | --- |
| A 单 Agent | 15/15 | 100% | 1.0 (n=15) |
| B 多 Agent | 15/15 | 100% | 1.0 (n=15) |
| C 向量 RAG | 15/15 | 100% | 1.0 (n=15) |
| **FULL 混合+重排** | **11/15** | **73.3%** | **1.0 (n=11)** ← 假的 |

聚合只统计 completed，所以成功画像的成功率永远是 1.0。
**必须看 n，不看只看 mean。**

### 3.14.4 修复的缺陷：报告隐藏非 completed 的运行

跑完时报告写「运行总数 60 / 完成 56 / 失败 0 / 不完整 0」——
**56 + 0 + 0 = 56 ≠ 60**，4 个 run 消失，第 4 节还说「无失败或不完整运行」。

根因：`reporting.py` 只认 `status == "failed"`，而 `waiting_human` 既不是
`completed` 也不是 `failed`，从三个桶里全部漏掉。

修法：计数改成互补分桶（未完成的必落进 failed/incomplete/其他状态），
第 4 节点名列出，并加统计口径提醒。3 条测试锁住，回退则 2 条变红。

### 3.14.5 显著性：只有成本和重试显著

引用质量类指标（`citation_resolvability` / `evidence_coverage`）**全部不显著**
（p = 0.18 / 0.32 / 0.066 / 0.5 / 0.125）。

显著项只有 `duration_ms`（p=0.0067~0.0244）与 `retries`（p=0.0253~0.0339）。

**如实结论**：n=15 下没有统计证据表明多 Agent / RAG 提升引用质量，
能确认的只有「更慢、重试更多」。
