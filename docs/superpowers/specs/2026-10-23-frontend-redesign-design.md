## 1. 背景与诊断

用户要求「把页面优化一下，前端重新设计」，并指定风格参考
<https://asharca.github.io/ui/>（beUI）。

先用 Playwright 截取服务器真实页面（6 个核心页 + 移动端），确认现状问题：

### 问题 1：任务列表是「同质化墙」

20 行里有 19 行标题几乎一样（`检索增强生成评估方法综述（…复验 #3）`），
唯一区分靠括号后缀，而它被排成普通正文。

### 问题 2：进度条说谎

`taskProgress(status)` 是**从状态映射的百分比**，不是真实进度：

```ts
failed: 100,      // ← 失败也显示 100% 满格蓝
completed: 100,
```

视觉上「失败」和「完成」的进度条**一模一样**。这列几乎不传递信息。

### 问题 3：侧栏 9 项同权重平铺

`任务 / 知识库 / 引用样式 / Word 模板 / 导入文献 / 团队 / 用量 / API Key / 我的套餐`

「任务」是每天用的，「API Key」配一次就不动 —— 平铺让日常路径淹没在设置项里。

### 问题 4：登录页没有产品身份

白底一张卡片，看不出这是「生成即合规、引用可核验」的学术工具。

### 问题 5：整体「装了 shadcn 但没做设计」

Nova 中性基调没错（AGENTS §6.5 要求安静、不抢注意力），但**没有层次**：
标题、正文、表格、卡片几乎同一灰度，视线没有落点。

## 2. 设计语言：beUI 的三条特征

参考 beUI 的**视觉语言**，不取其代码 —— 它是 React + Framer Motion，
本项目是 Vue，动效统一走 motion-v（AGENTS §6.5.2）。

从渲染后的页面提取真实 token（`extract_tokens` 脚本，见执行记录）：

| 特征 | beUI 取值 | 本项目落地 |
| --- | --- | --- |
| **6% 发丝边框** | `oklch(15% 0 0 / .06)` | 同（`--border`），另留 `--border-strong` 12% 用于需要明确分割处 |
| **卡片略亮于底色** | 底 99% / 卡片 97% | 底 98.5% / 卡片 100%（靠「更白」产生层次，不靠阴影） |
| **高对比文字 + 低对比线条** | 文字 15% / 线条 6% | 同 |
| 主色 | `#0285f7` 亮蓝 | `oklch(0.62 0.19 250)`（比旧 Nova 沉蓝更醒目） |
| 徽标 | 药丸形 + 淡色底 | 沿用既有 `success/warning/destructive` 淡底变体 |
| 导航 | 微缩大写分组标签 | 同（`text-[11px] uppercase tracking-wider`） |

## 4.5 任务列表页（第二阶段，已交付）

原计划留作第二步，本轮做完。**三个真问题**及修法：

### 问题 1：同质化标题墙 → 主标题 + 次级灰字

拆分逻辑抽成 `splitTaskTitle()` 纯函数：

- 按**括号深度**只拆最外层（`综述（第一轮（含附录））` → main=`综述`，
  meta=`第一轮（含附录）`，不会把主题切碎）；
- 全角 `（）` 与半角 `()` 都识别；
- **括号不在末尾时不拆**（`综述（草稿）补充说明` 的括注属于主题的一部分）；
- 括号内容为空、整个标题就是括号时都不拆。

### 问题 2：进度条说谎（最严重）

旧实现：

```ts
failed: 100,      // 失败也显示 100% 满格蓝
completed: 100,   // 与完成视觉完全相同
```

`taskProgress()` 是从状态映射的**常量**，不是真实进度 —— 这一列几乎不传递信息。

修法：

- **终态用形状图标**（✓ / ✕ / ⊖）。形状比颜色可靠：色盲用户、灰度打印、
  深色模式下都分得清；
- **只有进行中**才显示百分比条 —— 此时百分比才真有意义。

### 问题 3：没有汇总 / 筛选 / 搜索

- 汇总卡 4 项。「待我确认」（`waiting_approval` + `waiting_human`）用警示色
  突出，因为它是**唯一**需要用户动手的状态；为 0 时也不隐藏（避免布局跳动）。
- 状态筛选分段控件带计数，可点；点汇总卡也能筛选。
- 标题搜索匹配**整条**标题（含被拆到次级标记里的后缀），用户按哪种都能搜到。
- 筛选无结果时给「怎么回到有结果」的引导 + 一键清除，不是空白表格。

### 问题 4：20 个重复的「打开」按钮

整行可点击 + hover 浮现箭头。但**行尾必须保留一个真正按钮**
（`aria-label="打开"`）—— 见下方两次回归的说明。

## 4.6 本轮踩的两个回归（都是我引入的，E2E 抓到）

### 回归 1：删掉「打开」按钮破坏了 E2E 契约

把右侧「打开」按钮改成纯装饰箭头后，`m2-result-preview` / `m2-all-preview`
用 `getByRole("button", { name: "打开" })` 定位 → 超时失败。

第一次修的时候又踩了第二个坑：给行加 `role="button"` 让整行可访问，
结果同一行出现**两个** button 角色，`getByRole` 命中多个 → 二义性。

**最终方案**：行本身 `cursor-pointer + @click`（不是 role=button），
行尾放一个 `aria-label="打开"` 的真按钮。

### 回归 2：视觉去重不能删 DOM 里的信息

为去掉 `✓ 已完成` 的视觉重复，我把终态文字**从 DOM 删掉**了。后果：

- `m2-result-preview` 按行文本含「已完成」遍历找已完成任务 → 匹配不到，
  退到打开第一条（当时是 `waiting_human`，没有结果页）→「结果」页签被禁用 → 失败；
- 无障碍退化：读屏软件读不出 SVG 图标语义，终态没有任何可读文字。

**最终方案**：终态文字改用 `sr-only`（视觉隐藏、DOM 保留）——
视觉干净、读屏可用、E2E 契约保住、页面内 Ctrl+F 也能搜到。

> **教训**：视觉去重 ≠ 删信息。`sr-only` 是这两件事的正解。

## 4.9 任务详情页重设计（第三阶段，已交付）

详情页是核心工作界面，也是本轮**发现最多真缺陷**的一页。三个缺陷全部来自截图实测，
不是版式偏好。

### 缺陷 1：结果页把 Markdown 当纯文本渲染（影响最大）

`TaskResult.vue` 用 `<pre>{{ final_markdown }}</pre>`，注释写的原因是「不用 v-html」
（安全考虑）。但用户看到的是一篇**带井号和星号的综述**：

```
# 检索增强生成评估方法综述
## 摘要
**[E1] Ragas 提出...**
```

这是核心产出页（`final_markdown` 是任务最终交付物），可读性影响最大。

**修法**：`marked` 解析 + `DOMPurify` 白名单消毒，两段式后才允许 `v-html`。

| 层 | 作用 |
| --- | --- |
| `marked.parse()` | Markdown → HTML（GFM：表格/删除线） |
| `DOMPurify.sanitize()` | 白名单消毒：只留排版标签，禁 `script`/`style`/`iframe`/`form`，禁事件属性 |
| 后处理 | 外链统一 `target="_blank" rel="noopener noreferrer"` |

新增「源码」切换：渲染视图是默认，但核对引用标记时仍需看原始 Markdown。

### 缺陷 2：执行 tab 的 DAG 被裁切，5 个节点只显示 3 个

日志页显示 n1~n5 **全部完成**，但 DAG 只画出前 3 个。

**根因**：链式任务 5 个节点 = 5 列，宽度 `5×200 + 4×96 = 1384px`，而容器约
1100px → 右侧 n4/n5 被裁掉。横向滚动条在视觉上几乎不可见，用户会以为
「任务只跑了 3 步」。

**修法**：`layoutDagAdaptive()` 按容器实测宽度（`ResizeObserver`）自动换向：

- 横向放得下 → 保持横向（多分支图仍是最佳方向）；
- 放不下 → **换向纵向**（拓扑深度铺成行），链式任务自然变成一列从上到下，
  不需要任何滚动，窄屏也友好。

边路径按方向分别计算（沿用在横向假设下的控制点，纵向会画出穿出容器的线）。

同时去掉旧的「适应窗口」缩放按钮 —— 它把节点文字一并缩小，反而更难读。

### 缺陷 3：批注面板占满每个 tab 底部

四个 tab 下面都挂着完整批注面板（含大块空态），把「结果」「日志」挤得很长。
批注属于协作场景，不该在所有 tab 抢占纵向空间。

**修法**：改侧边抽屉，默认收起，头部有入口按钮。`AnnotationPanel` 新增
`bare` 属性（默认 `false`，既有调用方行为不变），抽屉传 `bare`，
避免重复显示「导师批注」标题与外框。

### 附带：头部补「待我确认」提示

以前只靠状态徽标暗示，容易被忽略。现在 `waiting_approval` / `waiting_human`
时显式提示「规划已生成，等你确认后开始执行」+ 跳转按钮。

## 4.10 依赖变更：marked + dompurify

两个都是 MIT、**零运行时依赖**。体积影响：gzip +33KB（109→145KB），可接受。

### 本机没有 npm 的处理（重要）

AGENTS §6.5.6 规定前端**只用 npm**（CI 与 Dockerfile 都跑 `npm ci` +
`package-lock.json`），并明确禁止重新引入 `pnpm-lock.yaml`（历史上它导致镜像
构建失败）。

但本机只装了 pnpm，没有 npm。做法：

1. 用 pnpm 把包装进 `node_modules`（仅供本地开发/测试）；
2. **删除** pnpm 生成的 `pnpm-lock.yaml`；
3. 手工把两个依赖写进 `package-lock.json`，版本与 `integrity` 全部从
   npm registry 现取（不猜）；
4. 用脚本校验「`package.json` 的 14 个依赖全部在 lock 里有条目」。

CI 的 `Frontend Unit, Types & Build` 与 `Docker Build Check` 都通过 →
证明 lock 与 package.json 一致。

## 4.11 第三阶段踩的坑（都靠复查发现）

### 坑 1：DOMPurify 在 happy-dom 下静默剥标签

`dompurify` 需要真实 DOM。实测：

| 环境 | `isSupported` | 行为 |
| --- | --- | --- |
| 浏览器 | `true` | 正常消毒 |
| 纯 Node（无 DOM） | `false` | 实例不可用 |
| happy-dom（vitest 默认） | **`true` 但剥标签** | 静默把 `<h1>` 变纯文本 |

第三种最危险：看起来「消毒成功」，其实渲染坏了。

修法：实现里做**能力探测**（探针 `<h1>` 消毒后必须仍含 `<h1`），
探测不过就走**保守降级** —— 输出转义纯文本（宁可少渲染，不可不安全，
也不可静默丢格式）。测试同时覆盖两条路径。

真实浏览器（Playwright）验证：`h1=1, h2=3, strong=26`，渲染正常。

### 坑 2：节点加高后又裁切一次

把节点高从 68px 加到 84px（两行标题不挤压元信息行）后，
5 个纵向节点 = `5×84 + 4×40 = 580px`，而容器上限 `max-h-[520px]` →
**又只能看到 4 个**。改用 `max-h-[70vh]`（900px 视口约 630px）后 5/5 可见。

> 同一个「裁切」问题在两轮里以不同原因出现两次 —— 说明**高度/宽度上限
> 都必须在真实数据上量过**，不能凭感觉设。

### 坑 3：E2E 依赖「打开」按钮与批注标题可见

- 删掉右侧「打开」按钮 → `m2-*` 用 `getByRole("button", { name: "打开" })` 失败；
- 批注改抽屉后 → `team-workspace` 直接断言「导师批注」heading 可见失败。

两处都是**设计变更导致既有契约失效**，属于合理更新测试（不是让实现迁就旧测试），
但必须显式改测试并说明原因。

## 4.12 知识库页重设计（第四阶段，已交付）

这一页的**主角不是版式，是一个把谎言做成 UI 的缺陷**。

### 缺陷：索引状态硬编码为 `True`

```python
return KnowledgeStatsOut(
    total_docs=total_docs,
    total_chunks=total_chunks,
    vector_index_ready=True,   # ← 硬编码
    bm25_index_ready=True,     # ← 硬编码
)
```

无论真实索引状况如何都报「就绪」。

**为什么这是本会话最该警惕的一类缺陷**：已经踩过完全同类的坑 ——
SQLite 有 28344 条 `vector_index`、Chroma 实际只有 **4** 条向量，而
`index_status` 全是 `ready`。数据库在撒谎，向量检索对全体用户静默失效，
最后靠「实验跑不出引用标记」才偶然追查到。

如果知识库页展示这个硬编码 `True`，用户会看到「索引就绪」，而语义检索是坏的。

**修法**（全部来自可验证事实）：

| 字段 | 真实算法 |
| --- | --- |
| `vector_index_ready` | 该用户 `vector_index` 行数 **==** `doc_chunk` 数，且 > 0 |
| `bm25_index_ready` | 进程内 BM25 索引确实就绪；**查不到时报 false**（「确认不了」不该显示成「就绪」） |
| `index_failed_count` | `index_status == "failed"` 的文档数（需重新上传） |
| `indexing_count` | `index_status == "indexing"` 的文档数（只需等待） |

### 前端改进

1. **汇总卡三张**：文档/分块、**需要处理**（索引失败，>0 时警示色 ——
   这是唯一需要用户动手的）、向量索引状态（显示后端实算值）。
2. **搜索 + 类型筛选**：搜索同时匹配**标题与原始文件名**（用户按哪个记都能搜到）；
   类型按钮带计数；筛选后显示「显示 N / M 篇」并给一键清除。
3. **标题去噪**：`original_name` 与 `title` 实质相同（只差扩展名）时不渲染第二行。
   实测 **11 篇里 10 篇**是这种重复 —— 等于白占 10 行高度。
4. **常量列隐藏**：`source` 全为 `upload` 时整列不显示（实测全部相同）。
5. **类型用徽标**：`pdf` → `PDF`。

### 为什么上传表单不收起来

E2E `literature-review` 直接操作 `document-file` / `document-title` /
`document-submit`，收进折叠面板会破坏它；而上传本来就是这页的主要动作，
常驻更合理。**这条是明确权衡过的取舍，不是遗漏。**

## 4.13 团队工作区重设计（第五阶段，已交付）

这一页**6 个缺陷全部是实测复现**的，其中一个属于「测试自己掩盖了缺陷」。

### 缺陷 1（最严重）：slug 自动派生完全失效

派生挂在 `@input="syncSlug"`，`syncSlug` 读 `newName` 这个 ref。而浏览器的执行
顺序是 **模板 `@input` 监听器先于 `v-model` 的写入**（模板事件在 `mountElement`
阶段注册，`vModelText` 指令的监听在 `created` 钩子里更晚）。

所以 `syncSlug` 读到的永远是**上一个字符**：

| 输入方式 | 后果 |
| --- | --- |
| Playwright `fill()`（整段值 + 单次 input） | 读到空串 → slug 为空 → 创建报「请填写团队名与标识」 |
| 真实逐字输入 | slug 永远少最后一个字符（实测断言 `'ab' !== 'abc'`） |

**既有单测为什么没抓到**：它写成「`setValue` 后再 `trigger('input')` 一次」
—— 第二次触发时 ref 已更新，缺陷被掩盖。这是典型的**假测试**（AGENTS #13）。

修法：改 `watch(newName)`，ref 更新之后才推导，与事件顺序解耦，对粘贴 /
自动填充 / 程序化赋值都成立。

### 缺陷 2：中文团队名派生不出 slug

`replace(/[^a-z0-9-]+/g, "-")` 后中文名得到 `"----"`，去首尾变空串。
用户被迫自己想一个英文标识。

修法：推导为空时兜底 `team-<6 位 base36>`，保证「只填名字也能创建」。

> **断言陷阱**：最初只断言 slug「非空 + 字符集合法」，而 `"----"` 两条都满足。
> 诚实性验证发现后补上「**必须含字母或数字**」才真正抓得住回退。

### 缺陷 3：退出团队后立刻报「工作区不存在」

`handleLeave()` 成功后调 `refresh()`，而 `refresh()` 会 `GET /workspaces/{id}` ——
此时用户已不是成员，后端按「不泄漏存在性」统一返回 404。
于是「退出成功」紧跟一条错误横幅。

修法：成功后 `router.push` 回列表；失败才留在原页显示原因。

### 缺陷 4：席位已满时列表页仍能生成邀请码

详情页对 `seat_used >= seat_limit` 做了禁用，列表页漏了 → 用户生成一个
**兑不了**的码（对方 accept 时超席位被拒）。

### 缺陷 5：邀请码有效期从未展示

接口返回 `expires_at`（默认 7 天），两个页面都没显示 —— 用户以为永久有效，
过期后对方兑不了还找不到原因。

### 缺陷 6：席位提示用硬编码颜色

`text-amber-600` 违反 AGENTS §6.5.3「只用 tokens，不写一次性颜色」，
深色模式下对比度不足 → `text-warning`。

## 4.14 用量看板重设计（第六阶段，已交付）

> 交接文档把这一页排在**风险第一位**：*「与知识库页同类风险最高：图表/计数最容易
> 出现『显示的数字与实际不符』，用户很难自己发现」*。
> 实际情况比预估更糟：**页面上最重要的那个数字从来就是错的**。

### 缺陷 1（最严重）：「累计 token」永远是 0，因为后端从来没记过用量

**现象**：`/observability/overview` 返回 `tokens.total_used = 0`，页面显示「累计 token 0」。
看起来像「这个用户还没用过」——**这正是它危险的地方**：0 是一个合理的值，
用户不会怀疑，而且没有任何报错。

**取证**（服务器真实数据，不是推理）：

```sql
-- task.used_tokens 全为 0
SELECT count(*), sum(used_tokens), count(*) FILTER (WHERE used_tokens>0) FROM task;
--  53 | 0 | 0

-- 但子任务载荷里明明有 token
SELECT sum((output_data::jsonb->'output'->'execution_result'->>'prompt_tokens')::int)
     + sum((output_data::jsonb->'output'->'execution_result'->>'completion_tokens')::int)
FROM subtask WHERE output_data IS NOT NULL;
--  169372
```

**根因**：`sum_actual_tokens()` 读的是 `output["prompt_tokens"]`（顶层），
而生产载荷（`LiteratureNodeExecutor._run`）把 token 放在
`output["execution_result"]["prompt_tokens"]`（嵌套）。

**为什么既有测试没抓到**（AGENTS §5 #13 的又一实例）：
`test_quota_correction_on_completion.py` 的三条用例，载荷全是
`{"prompt_tokens": 100, "completion_tokens": 50}` —— **测试替身的形状**，
生产从来不是这样。三条用例全绿，缺陷一直在线上。

**后果有两层，第二层比第一层严重**：

| 层 | 后果 | 严重性 |
| --- | --- | --- |
| 看板 | 「累计 token」永远 0 | 用户看到错数字但不会怀疑 |
| **配额结算** | 退款额 = `100k − used_tokens` = `100k − 0` → **每次都退满** | **用户白嫖全部算力** |

第二层是钱的问题，而且和看板是同一个根因——修一处，两层同时好。

### 缺陷 2：状态分布漏状态 → 看板自相矛盾

旧契约只给 4 个固定状态（completed / failed / cancelled / waiting_human）+ total。
实测 demo 有 **1 个 `waiting_approval`**，不在契约里：

```
任务总数 27
状态分布：已完成 20 + 待人工 4 + 已取消 2 = 26   ← 差 1 个，差值不可见
```

用户不可能发现少了一个——因为**页面没有显示「合计」**，两处数字不在一起。

### 缺陷 3：成功率没有分母

显示 `76.9%`，但分母是 26 还是 27？不告诉用户，用户没法核对，
而 26 这个数字来自「只算已进入终态的任务」这条业务规则。

### 缺陷 4：最近任务只有 8 位 UUID

```
2361d17a  待确认规划  0 token      13 秒
2aa48e0a  已完成      5,346 token  1 分 30 秒
```

一整列 `2361d17a`、`2aa48e0a` —— **认不出哪条是哪个任务**。
数据库里明明有 `title`，只是没返回。

### 缺陷 5（本阶段自己引入，靠取证抓到）：耗时 9708 分钟

回填脚本跑完后，页面显示「9708 分 12 秒」（约 6.7 天），而真实耗时 90 秒。

根因：`Base.updated_at` 带 `onupdate=func.now()`，**Core 的 `update()` 也触发它**。
回填 `used_tokens` 时把 28 个历史任务的 `updated_at` 全刷成同一时刻，
而耗时用 `updated_at - created_at` 计算。

这不只是「统计不准」：`updated_at` 是审计字段，任务列表的「更新时间」也用它。
**回填脚本污染了业务数据**。已用 `restore_task_updated_at.py` 恢复（依据
`completed_at` → `execution_log.logged_at` → `subtask.updated_at`），
并修好脚本本身（显式写回 `updated_at=Task.updated_at` 压掉 onupdate）。

> 教训：**写库脚本必须核对「只改了想改的那一列」**。
> 这次是因为「量数值」量到 `9708 分` 才发现的 —— 只看「回填成功 28 行」不会发现。

### 缺陷 6（自己引入，靠结构取证抓到）：任务行键盘不可达

首版把行做成 `<li @click>`。用 `FOCUSABLE` 导出实测：

```
FOCUSABLE=[…, {tag:"BUTTON", testid:"observability-refresh"},
           {tag:"BUTTON", testid:"observability-row-…"}]   ← 修复后才有
```

修复前该列表里**没有任何一行任务** —— 键盘用户完全进不去任务详情，
违反 AGENTS §6.5.3「所有可交互元素键盘可达」。改成 `<button type="button">`。

## 4.15 套餐页重设计（第七阶段，已交付）

> 交接文档排第 2 位，理由：**涉及金额，显示错了是信任问题**。
> 实际查下来，金额本身没算错（分转元正确），但**这一页几乎不回答用户的问题**。

### 取证方法（先量数据，不改版式）

按交接文档的提醒，先打真实接口 + 用 Playwright 把渲染结果**结构化导出**，
再用「接口值 vs 页面值」的差异找缺陷。

真实数据（服务器）：

```
demo      → institution / monthly_reviews=-1 / reviews_used=3 / period_end=2026-11-22
e2efull   → free / monthly_reviews=1 / reviews_used=1 / reviews_remaining=0
其余 25 个用户 → 无订阅（免费档）
```

### 缺陷 1（最影响决策）：当前套餐卡**没有任何权益**

取证：

```
DEMO_CURRENT_CARD = {text:"机构版 2026-10 3 / 不限 篇",
                     mentionsTeam:false, mentionsApi:false,
                     mentionsSeats:false, mentionsWorkspace:false}
```

而下面「可选套餐」的每张卡都列了团队/API/席位。用户要判断「我该不该升级」，
必须**自己拿当前套餐名去四张卡里对照找**——页面上没有直接答案。

**根因不在前端**：`UsageOut` 只返回 6 个字段（用量 + 名字），权益字段一条没给。
这些字段 `Plan` 表里本来就有，只是 `get_usage` 没返回。

**为什么不让前端自己补**：前端拿 `plan_id` 去 `plans` 列表里查，等于维护
**第二份套餐配置**——后端改价/改权益时前端会静默显示旧值。这类「两份配置」
在知识库页（硬编码 `vector_index_ready=true`）已经踩过一次。

### 缺陷 2：没有订阅到期日，用量周期被当成到期日

取证：页面当前卡文本只有 `机构版 2026-10 3 / 不限 篇`，**没有任何日期**。

`period_key`（`2026-10`）是**用量**周期（自然月，篇数按月重置），
而订阅到期日是**购买日 + 30 天**。demo 的实际到期日是 `2026-11-22`。
用户看到 `2026-10` 会以为「10 月底才需要续费」。

### 缺陷 3：额度用尽，进度条还是「健康蓝」

取证：

```
FREE_PROGRESS_BAR = {width:"958px", backgroundColor:"oklch(0.62 0.19 250)"}
                  ↑ 这就是 --primary 主色蓝
```

额度 100% 用尽的进度条与「用了一半」长得一样，**扫一眼不会警觉**。

修法：`isExhausted`（`reviews_remaining === 0`）时用 `bg-warning`。
**不是「越高越红」**：工作台里 80% 是常态，天天红会让警示失去意义；
只有「已经不能再跑任务」这个状态才需要立刻吸引注意。

### 缺陷 4：文案说「升级」，页面上**没有任何升级入口**

取证：

```
FREE_ACTIONS = [9 个导航 <a>…, {tag:"BUTTON", text:"", testid:null}]
                                                 ↑ 退出登录（空文本）
```

文案写「升级套餐可立即继续」，但用户**没有任何办法升级**。
（本项目无在线支付，开通走管理员手工——但那也得告诉用户怎么操作。）

修法：引导条里加一个真按钮「查看可升级套餐」，点击滚动到对比区；
并在对比区标题旁写明「当前为手工开通（暂无在线支付）；如需升级请联系管理员开通」。

### 缺陷 5：加载中页面空白

取证（两个接口各延迟 3s）：

```
LOADING_STATE = {text:"我的套餐可选套餐", textLen:8,
                 hasLoading:false, hasSkeleton:0, hasSpinner:0}
```

3 秒里用户看到两个标题和一片空白，不知道是在加载还是坏了。

### 缺陷 6：usage 失败连坐套餐列表

取证（只让 `billing/usage` 返回 500，`billing/plans` 正常）：

```
ERROR_STATE = {planCardCount:0, hasPlansButNoUsage:false}
```

`Promise.all` 里任一失败就整体进 catch，`plans` 明明成功了也被丢掉 ——
**用户在最需要看套餐的时刻看不到套餐**。

修法：`Promise.allSettled`，谁失败报谁，能显示的照常显示。

## 4.16 引用样式页重设计（第八阶段，已交付）

> 交接文档排第 3 位，理由：**展示型，风险低**。
> 实际查下来，缺陷不在"展示得好不好看"，而在**这一页最该展示的东西没有展示**。

### 缺陷 1（最严重）：完全没有预览

取证（Playwright 结构导出）：

```
HAS_PREVIEW_WORD = false
CLICKABLE = [9 个导航 <a>, {BUTTON 上传样式}, {BUTTON 退出登录}]
            ↑ 每个样式行既不可点、也不可展开
VISIBLE_TEXT = [..., "gbt7714-2025-numeric", "citation-number · citation-order · zh-CN", ...]
```

6 个样式在页面上**只有名字 + 三个元信息字段**。

**为什么这很严重**：`gbt7714-2025-numeric` 与 `gbt7714-2015-numeric` 的
numbering / ordering / locale **完全相同**（实测 `META_DISTINCT = 5/6`），
用户光看 `citation-number · citation-order · zh-CN` **分不出区别**。
而两者的真实输出差异明显：

```
2025 版：[1] 牛 耕田, 李 四. 检索增强生成评估方法综述[J]. 计算机学报, 2024, 47(3): 1-20.
2015 版：[1] 牛 耕田, 李 四. 检索增强生成评估方法综述. 计算机学报, 2024, 47(3): 1-20.
                                                  ↑ 没有 [J] 类型标识
```

用户在选择界面上无法获得做决定所需的信息。

### 缺陷 2：删除没有确认

取证：删除按钮直接 `@click="handleDelete"`，**没有任何确认**。
后端 `service.delete` 会 unlink 磁盘文件 —— 误点一下就得重新上传。

### 关键决策：预览由**后端**渲染

导出走 `CitationRenderer`（citeproc + 真实 `.csl`）。如果前端另写一套格式化器：

- 等于维护**第二份 CSL 实现**，必然与导出漂移；
- 用户会看到「预览长这样、下载出来不是」——**比没有预览更糟**。

所以新增 `GET /citation-styles/previews`，复用同一个 `CitationRenderer`。
这是唯一能保证「预览 == 导出」的做法。

### 样例文献为什么是固定的两条

预览是**样式之间**的比较，不是用户数据展示：

| 选择 | 理由 |
| --- | --- |
| 固定样例（不取用户文献） | 6 个样式的输出可直接横向对比，差异全来自样式本身；空库用户也能看到预览 |
| 中英各一条 | 能同时看出 locale 差异（GB/T 7714 中文著录 vs APA 英文著录格式差异最大）与作者名处理（全大写 / 缩写 / `&`） |
| 期刊 + 会议两种类型 | 能看出 `[J]` 与 `[C/OL]` 的类型标识差异 |
| 字段填满（卷/期/页/DOI） | 各样式「缺字段时省略标点」的差异也能看出来；只给题名则所有样式长得差不多 |

### `warnings` 为什么要透出到前端

`CitationRenderer` 在 citeproc 失败时**静默回退**极简格式化器，`render()`
依然返回**非空条目** —— 看起来完全成功。

**本轮真实踩到**：探针脚本里 `sys.path.insert(0, BACKEND_DIR)` 让 `app`
解析到镜像里 site-packages 的那份副本（**没有 `styles/` 资产**），
6 个样式**全部走兜底**，输出只有 2 种：

```
gbt7714-2025-numeric / gbt7714-2015-numeric / ieee / nature → 完全相同
apa / gbt7714-2025-author-date                             → 完全相同
SUMMARY: 6/6 样式渲染成功     ← 看起来完美
```

所以预览 API 必须把 `warnings` 透出来，前端显式提示「该预览可能未按样式渲染」。

### 修复前后实测对照（真实服务器 + 真实浏览器）

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 预览 | 完全没有（`HAS_PREVIEW_WORD=false`） | 6 条预览，每条 `w=966 h=80`，`textLen 225~267` |
| 样式可区分性 | 元信息 5/6 去重，两个国标分不出 | **`AFTER_DISTINCT = 6 / 6`** |
| 兜底告警 | 无从得知 | `AFTER_FALLBACK_WARNINGS = 0`（真实资产下无兜底） |
| 删除 | 一键直接删 | 二次确认（确认/取消） |
| 预览口径说明 | 无 | 「渲染 2 条样例文献（中文期刊 + 英文会议），与最终导出使用同一个渲染引擎」 |
| 溢出 | 0 | 0（桌面与移动均 0） |
| 预览对比度 | — | **18.86:1**（AA 要求 4.5:1） |

### 后端契约

```json
GET /api/v1/citation-styles/previews
{
  "previews": [{
    "style_id": "...", "title": "...", "source": "preset|custom", "is_default": false,
    "entries": ["渲染出的参考文献条目..."],
    "markers": {"sample-zh-journal": "[1]"},
    "warnings": []
  }],
  "sample_count": 2
}
```

- 顺序与 `GET /citation-styles` **完全一致**（前端按 id 对齐，不依赖下标）；
- 单样式失败只降级该条（`warnings` 里写原因），其余照常；
- **路由顺序**：`/previews` 定义在 `/{style_id}` 之前（FastAPI 固定路径优先的约定）。

## 4.17 Word 模板页重设计（第九阶段，已交付）

> 交接文档排第 4 位，标注「展示型」。查下来的缺陷同样不是版式，
> 而是**页面在骗用户**。

### 缺陷 1（最严重）：按钮承诺「渲染成稿」，实际产出占位文本

取证方法：上传真实模板 `school_template.docx`（7 个占位符），
**复现前端 `handleRender` 的载荷**，再解包下载的 docx 读正文。

前端发送的载荷：

```ts
sections[key] = "示例内容（key）"
bibliography = ["[1] 示例参考文献（references）"]
```

渲染出的成稿正文逐段：

```
目录占位内容
示例内容（title）
示例内容（abstract）
编号条目一
示例内容（chapter_1）
示例内容（chapter_1_1）
示例内容（body_main）
撰写人：示例内容（author）
[1] 示例参考文献（references）
```

**正文总字符数 129**。而页面上 `HAS_DEMO_WORD = false` ——
按钮叫「渲染」，成功提示叫「已用模板「X」生成成稿并开始下载」，
**用户完全不知道下载到的是占位文本**。

### 根因：缺陷 100% 在前端

后端契约是**严的**：`_validate_contract` 在缺占位符内容时直接拒绝——

```python
missing = sorted(keys - set(sections) - ({bibliography_key} if bibliography_key else set()))
if missing:
    raise TemplateRenderError(f"缺少占位符内容（拒绝静默丢内容）：{missing}")
```

即「绝不静默丢内容」这条原则后端已经守住了。缺陷在于前端
**主动填假内容去满足契约**，然后把这个结果标成「成稿」。
契约能防住「少填」，防不住「填假的」。

> 教训：契约校验的是**形状**，不是**真实性**。凡前端为了通过校验而
> 自己编内容，都是在制造假成功。

### 修法（用户确认的方向）：不假装

这一页**没有真实综述内容可用**——正文在任务里，参考文献由任务级引用样式渲染。
所以：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 按钮 | 渲染 | **校验模板** |
| 下载文件名 | `<名字>.docx` | `<名字>-校验.docx` |
| 成功提示 | 「已生成成稿并开始下载」 | 「校验通过，已下载填充**示例文本**的 .docx。该文件仅用于确认版式与占位符是否齐全，**不是**真实综述成稿；真实成稿请在任务详情页导出」 |
| 页面说明 | 无 | 顶部固定说明条，讲清「校验」与「真实成稿」的区别 |

**这个调用仍然是真实的结构校验**：后端缺占位符会 400 拒绝，
所以模板有问题会在这里暴露，不用等到真正导出时才发现。
按钮的价值保住了，只是不再谎称产出成稿。

### 缺陷 2：占位符只显示 key，后端给的 label 被丢掉

后端 `PlaceholderOut` 一直有 `label` / `required` / `sample` 三个字段
（`label` 最长 128 字符、`sample` 最长 500 字符），前端只渲染 `key`。
模板作者写的说明等于白写。

实测服务器返回的 `label` 全是空串（那份模板没声明），
但**前端不能因此永远不显示** —— 已改为优先用 `label`，为空才退回 `key`。

### 缺陷 3：删除无二次确认

后端 `service.delete` 会 `unlink` 磁盘文件。与样式页同类问题，已加二次确认。

### 修复前后实测对照（真实服务器 + 真实浏览器）

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 按钮文案 | `渲染` | **`校验模板`** |
| 页面提到「示例」 | `HAS_DEMO_WORD = false` | **`AFTER_HAS_DEMO_WORD = true`** |
