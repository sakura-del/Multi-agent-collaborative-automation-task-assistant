## 0. 先做范围校正（重要）

用户提出的 Phase 2 是「PRISMA 筛选工作台 / 引用图谱 / 开放 API」，但对照路线图：

| 用户说法 | 路线图实际归属 | 说明 |
| --- | --- | --- |
| PRISMA 筛选工作台 | **Phase 2** ✅ | 一致 |
| 开放 API | **Phase 2** ✅ | 一致（与 MCP server 同项） |
| **引用图谱** | **Phase 3** ❌ | 路线图 §5 Phase 3 明确列在「建生态」：*模板库与市场 · 质量/偏倚评估 · **引用图谱** · PDF 表格抽取 · 多语言 · 机构版* |

**本纲要按路线图为准**，把引用图谱留给 Phase 3；若你希望提前，需明确调整路线图。

Phase 2 真实范围是 **6 项**：

| # | 功能 | 价值 | 依赖 |
| --- | --- | --- | --- |
| 1 | **PRISMA 筛选工作台**（标题摘要 → 全文 → 纳入；双人独立 + 分歧解决） | ⭐ 填补「检索↔筛选断层」——竞品 Elicit 检索不跑 PRISMA、Rayyan 跑流程不检索 | 检索源（Phase 1 ✅） |
| 2 | **可复现检索日志 + PRISMA 流程图导出** | 方法学刚需（PRISMA 2020 要求报告检索式、库、日期、命中数） | 与 1 同源数据 |
| 3 | 团队工作区 + 席位 + 导师批注 | 团队版卖点 | 1（需要共享筛选对象） |
| 4 | MCP server + 开放 API + Key | 外部集成入口 | 无 |
| 5 | 计费套餐 | 商业化 | 4（配额已有） |
| 6 | 可观测性（指标/追踪/成本看板） | 运营必备 | 无 |

**建议顺序**：`1+2`（一个子计划，强耦合）→ `6`（低成本、立刻有收益）→ `3` → `4` → `5`。

理由：
- **1+2 必须一起做**：PRISMA 流程图的数据全部来自筛选记录（各阶段命中/排除数），
  拆开会导致「先做工作台、再补日志」时数据模型返工；
- **6 提前**：可观测性不依赖其他项，且能在后续所有项上立刻提供排障能力；
- **3 在 4 之前**：开放 API 的鉴权/配额模型要与「用户 vs 团队」身份对齐，
  先定团队再开放 API 更省事；
- **5 最后**：计费依赖配额与团队席位都定型。

## 1. 首个子计划：PRISMA 筛选工作台 + 可复现检索日志

详见 [2026-10-20-00b-phase2-prisma-plan.md](2026-10-20-00b-phase2-prisma-plan.md)。

**核心交付**

- **检索日志**：每次检索持久化「检索式 / 源 / 时间戳 / 命中数 / 去重后数」，
  可复现、可导出；
- **筛选工作台**：三阶段（标题摘要 → 全文 → 纳入）逐条决策，
  记录 `include / exclude / maybe` + 排除理由（PRISMA 2020 要求列出排除理由分类）；
- **双人独立筛选 + 分歧解决**：两名筛选者各自决策，系统标记冲突，第三人（或协商）裁决；
- **PRISMA 流程图导出**：按 PRISMA 2020 模板生成识别/筛选/纳入各阶段计数（SVG 或 Markdown 表格）。

**关键设计决策（已冻结）**

1. **筛选对象是「检索结果快照」而非实时检索**：检索结果落库为
   `screening_record`，筛选决策引用它。否则上游源变化会导致筛选记录漂移、
   PRISMA 数字无法复现。
2. **检索日志与筛选记录同表族**：`search_log`（一次检索）+ `screening_record`
   （一条候选文献）。PRISMA 各阶段计数全部由这两张表派生，**不另存汇总数字**
   （避免汇总与明细不一致）。
3. **决策是「追加式」而非覆盖式**：每次决策写一条 `screening_decision`
   （含筛选者、阶段、决定、理由），当前状态由最新决策派生。
   这样才有审计轨迹，也才能支持双人独立与分歧追溯。
4. **不自动筛选**：本项只做「工作台 + 记录 + 导出」，AI 辅助筛选属后续增强。
   PRISMA 要求人工决策可追溯，自动筛选需单独论证（且容易被质疑方法学）。

## 2. 其余 5 项的高层要点（暂不展开 Task 级）

### 2.1 可观测性（建议第 3 个做）

- 已有 `RequestIDMiddleware` 与结构化日志；缺的是**指标**（Prometheus 格式）
  与**成本看板**。
- 关键指标：任务成功率、各节点耗时分布、LLM token 消耗与成本、
  检索源错误率、限流命中数、配额拒绝数。
- 注意：不要引入重型 APM；`prometheus-client` + 现有结构化日志足够。

### 2.2 团队工作区 + 席位 + 导师批注

- 数据模型：`workspace` / `workspace_member`（role: owner/member/advisor）/
  `annotation`（挂在任务的产物或具体段落）。
- 难点是**权限模型**：现有所有查询都是 `user_id` owner-scoped，
  改成 workspace-scoped 是一次**全量重构**，需单独评估（建议先加
  `workspace_id` 可空列，逐步迁移，不做一次性切换）。

### 2.3 MCP server + 开放 API + Key

- API Key：`api_key` 表（只存哈希、可吊销、带 scopes），复用现有 Bearer 鉴权链路。
- MCP server：把现有能力（检索/建任务/取产物）暴露为 MCP 工具。
- 注意：MCP 与开放 API 是**两套入口、同一套服务层**，不要在服务层分叉。

### 2.4 计费套餐

- 依赖：配额（Phase 1 ✅）+ 团队席位（2.2）+ API Key（2.3）。
- 路线图 §6 定价原则：按成稿篇数计价、额度可结转、免费档 1 篇/月。
- 需要**计费事件表**（每次消耗记一条），不能只靠 Redis 计数（不可审计）。

## 3. 验收标准（Phase 2 整体）

- [ ] 用户能完成「检索 → 筛选 → 纳入 → 生成综述」完整闭环，且
      **PRISMA 各阶段数字可由系统自动生成并导出**

- [ ] 开放 API 有 Key 鉴权与配额，MCP 工具可用
- [ ] 关键指标可观测（任务成功率/成本/源错误率）
- [ ] 全量门禁：black/ruff/mypy/pytest（≥80% cov）+ 前端 + CI 6 作业全绿

## 4. 风险与已知约束

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **PRISMA 数字口径** | PRISMA 2020 对「识别/筛选/纳入」的定义很细（如重复记录数、自动化工具排除数），做错会被审稿人质疑 | 严格按 PRISMA 2020 流程图 27 个计数项设计数据模型；不省略「其他来源」分支 |
| **权限模型重构** | 团队工作区要求把 `user_id` owner-scoped 改为 workspace-scoped，触及几乎全部查询 | 分阶段：先加可空 `workspace_id`，双读单写，稳定后再切换 |
| **全文筛选成本** | 「全文阶段」需要 PDF 或全文文本，而版权约束下多数源只给元数据+摘要 | 全文阶段只对**用户上传**或**开放获取**的记录开放；其余记录明确标注「无全文」并记录该状态（PRISMA 允许） |
| **范围蔓延** | Phase 2 有 6 项、约 3 个月 | 每项独立子计划、独立验收；不把 Phase 3 的引用图谱提前 |
